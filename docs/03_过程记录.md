## 阶段 0：立项与调研（模拟 2025.2.5 – 2025.2.21）

### 0.1 立项背景（为什么是 2025 年 2 月）
- **时代背景**：2025 年春节前后 DeepSeek-R1 发布（1.20），2 月初华为云与昇腾上线 DeepSeek V3/R1，公司内部掀起 "DeepSeek + 业务场景" 落地潮，各部门被鼓励申报 AI 应用。
- **业务痛点**：
  1. 产线测试失败后，排查链路是 工厂测试工程师 → 设备部门 FAE → 研发，跨团队流转，**从提单到确认根因中位数约 2–3 天**（"数天"的来源）。
  2. 历史工单中沉淀了大量"现象 → 根因 → 措施"，但只能靠关键词在工单系统里搜，基本靠老员工经验。
  3. 新工程师 / 新产品导入期排障尤其慢。
- **为什么放在 Atebrain 应用层**：诊断请求天然带测试元数据（产品、工站、测试项、错误码），这些都在 Atebrain 里；平台已有 Kafka/ES/Redis/CCE，可复用。

### 0.2 需求澄清（需求评审结论）
| 类别 | 内容 |
|---|---|
| 输入 | 结构化元数据（产品型号、工站、测试项、错误码、测量值/上下限、设备 ID）+ 日志/现象文本 |
| 输出 | Top3 根因 + 置信度 + 每条根因引用的历史工单（可追溯）+ 建议排查措施 |
| 用户 | 测试工程师，手动发起，Web 页面 / 工单系统内嵌入口 |
| 性能 | 峰值 QPS 几十量级；**首字（首个结果）< 2s，完整结果 P99 < 5s** |
| 可用性 | 工作时间（工厂两班/三班倒，实际 7×24）服务可用 99.9% |
| 安全 | 工单含产品设计与客户信息，**必须内网私有化部署，禁止调用外部大模型 API** |
| 非目标 | 不做自动修复；不做多轮对话 Agent；不替代人工最终确认 |

> 安全这条直接决定了：只能用昇腾上私有部署的模型（DeepSeek / Qwen），这也是"为什么用 DeepSeek"的硬理由之一。

### 0.3 POC（2 周，TL + 用户 + 同事 B）
目标：验证"知识库 + 大模型"是否值得做，并摸清难点。

| 方案 | 做法 | 结果（在 300 条抽样黄金集上，Top3 命中率） | 结论 |
|---|---|---|---|
| P1 裸 LLM | 把请求直接给 DeepSeek-R1，不给知识库 | **≈ 25%** | 只会给通用答案（"检查线缆/重启设备"），不认识内部错误码，有幻觉 |
| P2 BM25 + LLM | ES 7.10 现有工单索引 BM25 召回 Top10 → DeepSeek-V3 | **≈ 52%** | 证明方向可行；错误码精确匹配效果好 |
| P3 向量 + LLM | 3 万条工单抽样 → bge-large-zh-v1.5 → FAISS 内存索引 Top10 → DeepSeek-V3 | **≈ 50%** | 同义表达（"无法上电"↔"开机失败"、"射频功率偏低"↔"TX power fail"）召回明显变好，但错误码/型号这类精确 token 召回变差 |

**POC 关键发现（决定了后面的架构）**：
1. **关键词与语义互补**：P2、P3 命中的样本重叠度只有约 60%，两路合并后理论上限明显更高 → 需要**双路召回 / 混合检索**。
2. **工单质量差**：现象描述口语化、错别字、中英混杂、大量"同上""已处理"无效内容 → 数据清洗是第一大工作量。
3. **R1 太慢**：R1 思维链动辄几十秒，满足不了 P99 < 5s；V3 直接输出质量也够用 → LLM 选型需要正式评估（阶段 1 十字路口 #2）。
4. **FAISS 只是 POC 玩具**：不支持增量更新、无持久化、无高可用、元数据过滤能力弱 → 正式方案需要向量库（阶段 1 十字路口 #1）。

### 0.4 评测集（黄金集）设计 —— 用户主导
没有评测集，后面所有"调参""换模型"都无从比较，所以这是立项后的第一件事。

| 项 | 设计 | 理由 |
|---|---|---|
| 来源 | 已闭环、根因经研发确认的历史工单 | 有可靠 ground truth |
| 规模 | **1,000 条**（POC 用其中 300 条） | 3 人团队能人工复核的上限；1,000 条时 Top3 命中率的 95% 置信区间约 ±2.8%，足以分辨 5 个点的提升 |
| 抽样 | 按产品线分层（基站、手机、平板、单板、芯片），每条线不少于 100 条 | 防止被某一产品线主导 |
| 防泄漏 | **按时间切分**：黄金集取 2024H2 闭环的工单；知识库只用 2024.6 以前的工单，且对黄金集做近重复检测剔除 | 模拟"用历史预测未来"，否则指标虚高 |
| 根因标准化 | 根因文本映射到**标准根因分类**（约 2,000 个根因类，由 FAE 专家维护的分类表 + 人工归并） | 不同工程师写法不同，必须按类匹配才能算命中 |
| 标注 | 用户 + 1 名 FAE 专家交叉标注，不一致的由 TL 仲裁 | |

### 0.5 指标口径（贯穿全项目）
| 层 | 指标 | 定义 |
|---|---|---|
| 检索 | Recall@K（K=10/50/100） | 召回的候选中包含"真实根因类"工单的比例 |
| 检索 | MRR@10 | 第一个正确候选排名倒数的均值 |
| 重排 | NDCG@10、Hit@5 | |
| 端到端 | **Top3 命中率** | 真实根因类出现在系统输出的 Top3 中的比例（**项目主指标，70% → 85% 即此口径**） |
| 端到端 | Top1 命中率、置信度校准度 | 置信度是否可信（如置信度 0.8 的结论实际正确率是否接近 80%） |
| 性能 | 首字时延、P99 端到端时延、可用率 | |
| 业务 | **排查时长** | 从发起诊断到工程师在工单上确认根因的时长中位数；对比基线：历史同类工单从提单到确认根因的中位数（约 2–3 天） |

> 关于"数天 → 2 小时"：这个对比口径是**系统给出的 Top3 中包含正确根因的工单**，工程师逐条验证即可确认，中位数 2 小时左右是合理的；未命中的工单仍走原流程。面试时要能说清楚这个口径，不要说成"所有故障都 2 小时解决"。

### 0.6 立项评审结论
- 立项通过，目标：**3 月底离线链路就绪，5 月灰度，7 月全量**。
- 首版目标 Top3 命中率 ≥ 70%（POC 52% 基础上，靠双路召回 + 重排 + 数据清洗 + prompt 提升）。
- 资源：昇腾 910B 推理卡（DeepSeek 推理由平台算力组统一部署，我们以服务方式调用；Embedding/Reranker 需要我们自己申请卡部署）。
- 风险登记：①工单数据质量 ②910B 配额排队 ③根因分类表维护成本 ④LLM 时延。

## 阶段 1：架构与选型（模拟 2025.2.24 – 2025.3.7）

### 十字路口 #1：向量库选型 —— 等待用户敲定

**约束回顾**
- 平台 ES 为 **7.10.2（CSS 托管）**：BM25 + IK 分词成熟，运维有人管；但**没有 HNSW**，`script_score` 暴力计算在 200 万条 × 1024 维上单次查询要几百毫秒到秒级，不可接受。
- 数据规模：100–200 万 chunk。BGE 系 1024 维 float32 ≈ **200 万 × 4KB ≈ 8 GB** 原始向量，加 HNSW 图约 10 GB —— 中小规模，单机放得下，但要求高可用。
- 需求：增量更新（每天有新闭环工单）、元数据过滤（按产品线/工站过滤）、高可用、关键词 + 语义双路。
- 团队只有 3 人：**运维负担**是一等公民。

**候选方案**

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| **A. ES 7.10（关键词路）+ Milvus 2.5（向量路），应用层融合** | 关键词检索继续用平台 ES；新引入 Milvus 2.5 在 CCE 上部署（Helm），存稠密向量 + 标量字段；应用层并发查询两路，用 RRF 融合 | ES 能力复用、零迁移；Milvus 专业、HNSW/IVF 齐全、支持标量过滤与增量写入；两路故障隔离（一路挂了可降级单路） | 多维护一套 Milvus（etcd + MinIO + Pulsar/Kafka 依赖）；两套存储要保证数据一致 |
| B. 只用 Milvus 2.5（稠密 + 内置 BM25 稀疏） | Milvus 2.5 新出的全文检索 + BGE-M3 稀疏向量，一个库做混合检索 | 一套系统、数据天然一致 | 2.5 于 2024-12 刚发布，中文分词（jieba）与 BM25 能力新、未经验证；放弃了平台 ES 现成的 IK 分词、同义词词典和运维支持 |
| C. 新建 OpenSearch 2.x（k-NN 插件）替代 | 一个引擎同时做 BM25 + HNSW | 一套系统，Apache 协议 | CSS 上 OpenSearch 版本可得性需确认；关键词路要从 ES 迁移；k-NN 插件在中文场景团队无经验 |
| D. FAISS 嵌入在线服务进程 + ES | 延续 POC，每个服务实例内存加载索引 | 最简单、最快（进程内查询 < 10ms） | 无持久化/增量更新需重建；每个副本 10GB 内存；过滤能力弱；多副本索引一致性要自己做 |
| E. GaussDB / openGauss 向量能力 | 用平台已有数据库 | 国产化、复用 DBA | 当时向量能力不成熟、成熟度和性能无据可依（见白名单"需确认"） |

**我的推荐：方案 A**，理由：
1. 关键词路是 POC 已验证的强项（52%），平台 ES 已有 IK 分词 + 运维，不该推倒重来；
2. 向量路需要的是成熟 ANN + 增量写入 + 标量过滤 + 高可用，Milvus 2.4/2.5 在 2025 年初是最成熟的开源选择；
3. 两路分属两个系统，天然**故障隔离**，可做"单路降级"——这也是高可用设计的一个亮点；
4. 代价是运维 Milvus：用 Milvus Operator / Helm 部署在 CCE，依赖的消息队列用平台已有 Kafka（Milvus 支持 Kafka 作为 MQ），对象存储用华为云 OBS（S3 兼容），实际新增运维面不大。
5. 方案 D（FAISS）作为**降级兜底**保留思路：真实项目中这是个好故事——"POC 用 FAISS，架构评审时因为增量更新和高可用被否，换成 Milvus"。

**请用户确认**：采用方案 A？或倾向其他方案？
