## 1. 现有条件盘点

设计的出发点：手里有什么、缺什么、受什么约束。

### 1.1 已有（可直接复用）
| 类别 | 已有 | 对本项目的意义 |
|---|---|---|
| 旧系统 | word2vec 智能诊断，准确率不到 70% | 有现成的工单数据接入、业务入口、用户习惯；也是**对比基线** |
| 知识库 | 约 50 万条历史工单（+ 手册/SOP） | RAG 的检索对象 |
| 搜索 | ES 7.10.2（CSS 托管），BM25 + IK 中文分词 | 关键词检索现成可用；**不支持 HNSW 向量检索** |
| 消息/计算 | Kafka、Flink、Spark、Hive | 离线批量处理与增量同步 |
| 存储/缓存 | GaussDB、Redis | 元数据/反馈存储、缓存 |
| 容器 | 华为云 CCE（K8s） | 部署、扩缩容、高可用 |
| 算力 | 昇腾 910B + MindIE | 模型推理 |
| 大模型 | 平台在昇腾上部署的 DeepSeek（以服务方式调用） | 生成与推理 |

### 1.2 缺少（本项目要补的）
| 缺口 | 说明 |
|---|---|
| 好的语义表示 | word2vec 词向量平均是旧系统的瓶颈 |
| 向量库 | 平台没有，ES 7.10 也做不了高效向量检索 |
| 重排能力 | 旧系统只有一次相似度排序 |
| LLM 编排 | 检索结果 → prompt → 解析 Top3 + 置信度 |
| 反馈闭环 | 工单上的反馈还没有回流利用 |

### 1.3 约束
| 约束 | 影响 |
|---|---|
| 3 人、6 个月（2025.2–7） | 少引入新组件，能复用就复用；运维负担是一等公民 |
| 工单数据涉密，必须内网 | 只能用私有部署模型，不能调外部 API |
| 并发低（工程师手动发起） | 不需要为高 QPS 过度设计，重点在**可用性和响应时间** |
| 开发语言 Python | 在线服务、离线处理脚本都以 Python 为主 |
| 技术时间线 | 只能用 2025.7 之前的技术（见 `02`） |

### 1.4 旧系统为什么不到 70%（决定新系统要解决什么）
| 旧系统短板 | 新系统对策 |
|---|---|
| 词向量平均：丢失语序和上下文，"电压偏高导致失败"和"失败导致电压偏高"几乎一样 | 换成上下文语义模型（BGE 系 embedding） |
| 错误码、型号等专有 token 没有词向量 | 增加**关键词检索路**（BM25 精确匹配） |
| 一次排序定结果，前几名不准就完了 | 先多召回，再用**重排模型**精排 |
| 只能照搬最相似工单的根因，不能综合 | **LLM** 阅读多条案例，归纳出 Top3 根因 |
| 相似度当置信度，不可信 | 置信度单独设计并校准 |

## 2. 设计目标（草稿，待确认）

| 维度 | 目标 |
|---|---|
| 准确率 | Top3 命中率：旧系统 < 70% → 新系统 ≥ 85% |
| 时延 | 首个结果 < 2s（流式），完整结果 P99 < 5s |
| 可用性 | 99.9%，任一依赖故障时可降级而非整体不可用 |
| 可解释 | 每条根因附带引用的历史工单 |
| 可迭代 | 工单反馈能回流，用于评测和微调 |

## 3. 总体架构（草图，待讨论）

```
                     ┌──────────────────── 离线链路（数据 → 知识库）────────────────────┐
 工单系统 / 手册  ──► │ 清洗去重 → 结构化抽取 → 切分 → Embedding → 写入 ES（关键词）+ 向量库 │
 （Spark 批量 / Kafka+Flink 增量）                                                      │
                     └──────────────────────────────────────────────────────────────────┘

                     ┌──────────────────── 在线链路（请求 → Top3）──────────────────────┐
 测试工程师 ─► 网关 ─►│ 诊断服务：构造查询 → 双路召回（ES BM25 ∥ 向量 ANN）→ 融合 → 重排  │
                     │          → 组装 prompt → DeepSeek → 解析 Top3 + 置信度 → 流式返回 │
                     │  Redis 缓存 · 超时与降级 · 限流                                   │
                     └──────────────────────────────────────────────────────────────────┘

                     ┌──────────────────── 反馈链路 ────────────────────────────────────┐
 工单上的反馈 ──────► │ Kafka → 反馈库 → 评测集更新 / Bad case 分析 / 微调数据            │
                     └──────────────────────────────────────────────────────────────────┘
```
对应 11 步：离线链路 = ①②③④；在线链路 = ⑤⑥⑦⑧；部署 = ⑨；反馈链路 = ⑩⑪。

## 5. 专题讨论

### T1：PDF 解析与切分（讨论中）

**为什么是难题**：知识库除工单外，还有大量 PDF（设备手册、测试规范、FA 失效分析报告、器件规格书等），里面混着正文、表格、图片、代码/命令/日志。
旧系统只把 PDF 当纯文本抽出来，表格被打散成一串数字、图片直接丢掉、代码被中文分词切碎——这些内容等于没进知识库。
这一步是离线链路"①数据源整理"的一部分，解析质量直接决定后面检索的上限（垃圾进、垃圾出）。

**PDF 来源的典型问题**
| 问题 | 例子 |
|---|---|
| 多栏排版、阅读顺序乱 | 规格书双栏，直接抽取左右栏文字交错 |
| 跨页表格 | 测试项参数表跨 3 页，表头只在第一页 |
| 扫描件 | 老版本手册、带签字的 FA 报告是扫描图片 |
| 页眉页脚水印 | 每页"华为机密 严禁扩散"、页码 |
| 图片承载关键信息 | 波形图、接线图、报错界面截图 |
| 代码/命令/日志 | 设备调试命令、寄存器配置、报错日志片段 |

**候选工具（均满足时间线 ≤ 2025.7）**
| 工具 | 发布 | 类型 | 优点 | 缺点 |
|---|---|---|---|---|
| PyMuPDF / pdfplumber | 成熟 | 规则抽取 | 快（每页毫秒级）、能拿到字体/坐标 | 版面复杂就乱；表格靠线框检测，无框表失效；扫描件无能为力 |
| Camelot | 成熟 | 表格专用 | 有框表格效果好 | 只管表格 |
| PaddleOCR / PP-Structure | 2022 起 | OCR + 版面分析 | 中文 OCR 强；Paddle 支持昇腾 NPU | 需要拼装流水线 |
| **MinerU**（OpenDataLab） | 2024-07 开源 | 版面检测 + OCR + 表格识别一体 | 中文文档效果好；输出 Markdown/JSON，自带阅读顺序、表格转 HTML、图片裁切 | 慢（每页秒级）；模型多，部署重 |
| Docling（IBM） | 2024-07 | 一体化解析 | 结构化输出好 | 中文与内网可得性一般 |
| Qwen2.5-VL（7B） | 2025-01 | 视觉大模型 | 能"看懂"图片并生成描述 | 慢、占卡；只适合少量关键图片 |

**推荐方案：分级解析 + 按元素类型分别处理 + 结构感知切分**

1）分级路由（快的处理简单的，重的处理复杂的）
```
PDF ─► 预检：有无文本层？版面复杂度（栏数、表格/图片占比）？
        ├─ 纯文本、版面简单  ──► PyMuPDF 规则抽取          （占多数，快）
        ├─ 版面复杂/表格多   ──► MinerU                    （慢但准）
        └─ 扫描件           ──► MinerU（OCR 模式，PaddleOCR）
```

2）按元素类型处理
| 元素 | 处理 | 入库形式 |
|---|---|---|
| 正文 | 去页眉页脚水印 → 恢复阅读顺序 → 识别标题层级 | 按章节切分 |
| 表格 | 转 HTML/Markdown；跨页表合并、补表头；小表整表一个 chunk，大表按行切并**每段重复表头** | 原表给 LLM 看；另生成一句话摘要用于向量检索 |
| 图片 | 过滤 logo/装饰图 → 抓图题（"图 3-2 …"）和上下文 → OCR 图中文字 → 关键图片用 Qwen2.5-VL 生成描述（二期） | 描述文本入检索，原图存 OBS，返回时附图片链接 |
| 代码/命令/日志 | 用等宽字体/版式识别代码块，**整块不切断** | 单独 chunk；关键词检索用不做中文分词的分析器，保留标识符、错误码原样 |

3）结构感知切分（chunking）
- 先按标题层级切成"节"，节内再按长度切；不在表格、代码块中间切。
- 每个 chunk 加上标题路径前缀：`《XX 设备手册 V3.2》> 第 5 章 射频测试 > 5.3 发射功率`，避免切开后丢失上下文。
- chunk 长度与重叠比例在 embedding 模型选定后（S2）再定，因为它受模型最大输入长度约束。
- 元数据：文档 ID、版本、页码、坐标、元素类型、产品线 → 用于过滤、引用溯源、文档更新时按文档 ID 整体替换。

**待用户确认**
1. PDF 的大致规模与类型（默认：数千份、数十万页；手册/测试规范/FA 报告/规格书；扫描件约 10–20%）
2. 是否认同分级解析方案；图片理解（VLM）放一期还是二期
