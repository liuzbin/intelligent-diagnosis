## 1.1 前身：旧版智能诊断系统【事实】
- 部门之前已有一个智能诊断系统，**基于 word2vec**，准确率**不到 70%**。
- 本项目的动机：**引入 LLM** 提升准确率。
- 因此效果指标 70% → 85% 的起点即旧系统水平（口径待与旧系统评测方式对齐）。
- 旧系统的具体实现（数据、存储、返回形式等）见第 12 节，待用户确认。

## 2. 业务背景

### 2.1 业务链路
```
部门提供测试设备 ──► 工厂用设备测试 产品 / 子产品 / 部件
                         │
          产品：通讯基站设备、手机、平板、单板、芯片等
                         │
            测试数据由设备客户端汇总 ──► 上传至云端 Atebrain
```
- 全平台数据量级：**每日 50 亿+ 条**（测试数据，非知识库）【事实】

### 2.2 Atebrain 三层架构【事实】
| 层 | 职责 |
|---|---|
| 底座 | Data ingestion（数据接入） |
| 中台 | 应用调度 |
| 应用 | 指标计算、利用数据 —— **智能诊断系统位于此层** |

### 2.3 平台已有组件【事实】
Kafka、Flink / Spark、Hive、Elasticsearch、Redis、K8s（华为云 CCE）、GaussDB。
- Elasticsearch 版本：**7.10.2（华为云 CSS 托管）**【事实，用户确认】→ 支持 BM25 全文检索与 IK 中文分词，但**不支持 HNSW 近似向量检索**（仅 script_score 暴力计算）
**没有向量库** → 需要在技术选型阶段专门讨论【待推演】。

## 3. 知识库

| 项 | 内容 | 标注 |
|---|---|---|
| 数据来源 | 以**历史故障工单**为主（半结构化：故障码 + 现象描述 + 根因 + 处理措施），辅以设备手册 / SOP 文档 | 假设 |
| 语言 | 中文为主，夹杂英文术语、错误码、测试项名 | 假设 |
| 规模 | 约 **50 万条**知识条目；切分后约 **100–200 万个 chunk** | 假设 |
| 与平台数据关系 | 知识库规模远小于平台 50 亿/日的测试数据；诊断时可能需要回查 Atebrain 中该设备/工站的近期测试数据作为上下文补充 | 假设（待推演确认是否纳入） |

## 4. 诊断请求与用户

| 项 | 内容 | 标注 |
|---|---|---|
| 用户 | **测试工程师** | 事实 |
| 触发方式 | 工程师手动发起 | 事实 |
| 请求内容 | 结构化元数据（产品型号、工站、测试项、错误码、测量值/上下限、设备 ID 等）+ 一段日志 / 现象文本 | 假设 |
| 并发 | **不高**（故障不会频繁发生）；按峰值 QPS 几十量级设计，留余量 | 事实 + 假设（数值） |
| 时延 | P99 端到端 3–5 秒以内（含 LLM 生成，可流式返回） | 假设 |
| 输出 | Top3 原因 + 置信度 + 依据（引用的知识条目） | 事实 + 假设（依据部分） |

> 说明：并发不高 ≠ 不需要高可用 / 降延迟。工程师在产线排障，**可用性和响应速度**才是重点；高并发主要体现在**离线入库的批量 embedding** 和**突发批量故障**（同一批次大面积失败）场景。

- 大数据平台团队共 20+ 人；**智能诊断系统 3 人**【事实】
- 用户本人是两名开发之一【事实】

**分工（Claude 提议，用户已确认 2026-10-14）**【事实】

| 角色 | 人 | 负责 |
|---|---|---|
| 负责人兼开发（TL） | 组长 | 立项与需求对齐、整体架构、LLM 选型与 prompt、跨团队协调（平台/算力/工单系统）、评审 |
| 开发 A | **用户本人** | **检索链路主力**：①数据源整理 ②embedding ③入库 ④建索引 ⑤retrieval（双路召回/混合检索） ⑥重排；以及 ⑩反馈数据回流 → ⑪Embedding/Reranker 微调 |
| 开发 B | 同事 | **服务工程**：在线服务框架、⑦prompt 工程落地 ⑧输出解析与置信度 ⑨部署（CCE、MindIE、高可用）、工单系统对接 |

> 理由：检索链路是 RAG 效果的决定性部分、技术点最密集（双路召回、混合检索、重排、向量库选型），也最容易在面试中被深挖；用户作为这条链路的 owner，同时参与 ⑦–⑨ 的联调与评审，保证 11 个阶段都有第一手认知。

## 9. 效果指标

| 指标 | 用户记忆 | 标注 |
|---|---|---|
| 准确率（Top3 命中率） | **70% → 85%** | 事实（模糊），具体口径待推演 |

## 12. 旧系统细节（待用户确认）

| 项 | 默认假设 |
|---|---|
| 算法 | 工单文本 jieba 分词 → 用工单语料自训 word2vec → 词向量平均得到句向量 → 与知识库余弦相似度 |
| 返回 | 最相似的 Top3 历史工单的根因，相似度当置信度 |
| 存储/检索 | 向量放在服务内存中暴力计算（numpy） |
| 知识库 | 与新系统同一批历史工单 |
| 主要短板 | 词向量平均丢失语序和上下文；错误码/型号等未登录词无向量；只能"照搬"相似工单的根因，不能综合多条案例推理；相似度不等于置信度 |
